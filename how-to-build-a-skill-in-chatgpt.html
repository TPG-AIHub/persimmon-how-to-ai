The Three Parts of Every Skill

Every skill is a document with three parts. Understanding what each part does — and why — is the difference between a skill that works reliably and one that fires at the wrong time or produces inconsistent output.

Name

Part 1 of 3
A short, recognizable label — like "Proposal Builder" or "article-summarizer."
How the skill is identified in your workspace and in conversations. Keep it short and specific. "Proposal Builder" is better than "Proposal Thing" or "Writing Helper."

Description

Part 2 of 3
A plain-language summary of what the skill does and when to use it.
This is what ChatGPT reads to decide whether the skill applies to a given request. The description controls whether the skill activates — so clarity here directly affects reliability.

Instructions

Part 3 of 3
The step-by-step process ChatGPT follows once the skill fires.
This is the actual logic — what to ask, how to format output, what rules to follow. The clearer and more specific the instructions, the more consistent the output.
Key distinction

The description controls whether the skill activates. The instructions control what it does once active. Both need to be clear on scope — and you'll often repeat some language across them on purpose.

You can also package reference files into a skill — a template you always want it to follow, or examples of what good looks like. The trade-off: if your template changes, you need to go back and update the skill. It's simple, but you have to remember to do it.

Understand the Structure

A Complete Working Skill

Here's a complete, working skill. It's intentionally simple — one job, no integrations — so you can see the three parts clearly.

The Name

article-summarizer

A short, hyphenated label that describes what the skill does, not what it's about. "article-summarizer" tells ChatGPT exactly the job this skill performs.

The Description

Description

Summarize a pasted or uploaded article into a structured brief. Always use when the user says "summarize this," "give me the takeaways," "what does this article say," "break this down for me," or pastes/uploads an article and asks for a summary. Accepts pasted text, .txt, .md, .pdf, or .docx files. Produces a markdown summary in chat. Do NOT use for book-length content, meeting notes, or transcripts — only articles and blog posts.
Notice three things: a plain-language statement of what it does, a list of real trigger phrases someone would actually say, and explicit boundaries on what it doesn't do. The imperative language ("Always use when…," "Do NOT use for…") is what pushes trigger reliability above 90%.

The Instructions

Instructions

Purpose: Turn an article into a structured brief that captures the argument, the evidence, and the so-what — not just the topic.

Accepted inputs: Pasted text, .txt, .md, .pdf, or .docx. If a file is uploaded, read it before proceeding. If the content is under 200 words, tell the user it's too short to summarize meaningfully and ask if they have the full article.

Output format — produce a markdown summary with these sections, in this order:

  • Title: The article's title, or "Untitled" if none is apparent.
  • Source: Author and/or publication, if identifiable. "Unknown" if not.
  • Point of View: What is the author's overall point of view, and how is it different from other common takes? Skip for purely informational articles.
  • Main arguments: 1–3 sentences per key point. What the author is actually claiming — not the topic, the claim. Based on what evidence?
  • So what: Why should this matter to me in my role?

What to avoid: Do not editorialize. Do not quote long passages — paraphrase, and quote only when exact wording matters. Do not pad sections: if the article presents no real evidence, write "None cited — argument is assertion-based." Do not add a closing line like "Let me know if you'd like more detail." Just end after the last section.

Written in imperative voice — direct commands, not suggestions. Notice the structure: purpose, inputs, output format (with exact sections in exact order), and explicit guardrails on what to avoid.
Build Your Own

Option 1: Use the Skill Builder

ChatGPT has a built-in Skill Builder that guides you through the process conversationally. It asks you questions and drafts the skill for you.

  1. Open the Skill Builder Go to Settings → Personalization → Skills → Create a Skill → "Use Skill Builder."
  2. Describe your task in plain language Example: "I want a skill that takes my raw client meeting notes and turns them into a structured summary with action items."
  3. Answer the follow-up questions The Skill Builder will ask about format, priorities, and rules. Answer naturally — you don't need special terminology.
  4. Review the draft The Skill Builder drafts the Name, Description, and Instructions. Read them carefully, make any edits, and save.
  5. Test it several ways Try different inputs and different phrasings of your request. A skill isn't done until it handles variation well.
Pro tip

Ask the Skill Builder to help you think through edge cases or exceptions. It's good at surfacing scenarios you might not have considered. For complex skills, expect to refine and redraft a few times as you use it.

Build Your Own

Option 2: Build from Scratch

Building a skill from scratch takes about 10–15 minutes after you've done it once. Here's the full process:

  1. Open ChatGPT Click the Business profile icon (bottom left) → Skills.
  2. Click "Skill" This opens the skill editor. You'll see existing skills listed; click to create a new one.
  3. Write a clear name Keep it short and specific. Describe the job, not the topic.
  4. Write the description 2–4 sentences. Explain what the skill does and the situations it applies to. Include imperative triggers: "Always use when…" and "Do NOT use when…"
  5. Write the instructions Step-by-step. What should ChatGPT do first? What questions should it ask? What format should the output take? Be explicit.
  6. Save and test Save the skill, open a new conversation, and try a request that should trigger it. Then try a request that should not trigger it.
  7. Refine as needed Most skills need a tweak or two after the first test. Edit the description or instructions and test again.
Build Your Own

Option 3: Build from a Live Chat

You don't have to stop what you're doing to build a skill. Some of the most useful skills get created mid-conversation — when you notice you're doing something you'll want to repeat.

Say you're deep in a chat — drafting a client recap, working through a piece of analysis — and you realize, "I'm going to want to do this exact thing again next week." You don't have to switch to the skills editor. Just tell ChatGPT, in that same conversation, that you want to turn what you just did into a skill.

Try saying

"Build a skill from what we just did — I want to be able to trigger this again later."

ChatGPT activates the skill-builder right there in the chat. It walks you through the same questions the standalone Skill Builder would ask, drafts the Name, Description, and Instructions based on the conversation you just had, and saves the skill when you're done. You keep your context, and you walk away with a reusable capability.

Keep It Working

Best Practices

Skills are easy to build. The harder part is building them well. These practices come from real experience with what works and what breaks.

  • Write descriptions that state when the skill applies — not just what it does. Include specific trigger phrases someone would actually say, and clear imperative rules about when ChatGPT must and must not use the skill.
  • Test in multiple scenarios before calling a skill done. Try phrasing your request several different ways. Try inputs that are close to the skill's job but not quite right — it should not fire for those.
  • Start with tasks you do repeatedly and already understand well. If you can describe the process clearly to a new colleague, you can turn it into a skill.
  • Keep each skill focused on one job. Narrow skills with clear triggers are more reliable than broad skills. One skill to build a course description, one to build a class outline, one to design exercises — not one skill that does all three.
  • Update skills when your process changes. A skill is only as good as its instructions. If the template changes, the skill needs to change too.
  • Name your skills consistently so the team can understand what they do at a glance.
Watch out

Don't build more than 20–30 skills (until the technology gets better). Too many can confuse ChatGPT about when to use what. Imperative directions help significantly, but you may see lower performance as you go past 30.

Updating & Shared Skills

When to update a skill

Skills need updating when your process changes, when you learn something new, or when the skill isn't performing the way you want. Here are the signs:

  • The skill fires at the wrong time (or doesn't fire when it should) — update the description or triggers.
  • The output is consistently off in the same way — update the instructions.
  • Your underlying process changed (new proposal format, new template) — update the instructions.
  • You've identified patterns the skill should catch but doesn't — add them to the instructions.

How to edit a skill

The easiest way: just tell ChatGPT you want to edit the skill. Always ask it to repackage the skill as a zip file that you can upload. The system will prompt you to confirm you want to replace the old version. Say yes.

Important: always request a zip file

If your skill includes reference files (like a template), they need to be bundled into the package. If you just ask ChatGPT to "update the skill," it may only give you the .md file (the instructions) and you'll accidentally replace a version that included your template with one that doesn't.

Shared skills on the team workspace

If you publish a skill to the Persimmon shared workspace that handles something multiple people do (like building exercises or formatting documents), keep these things in mind:

  • Get agreement first. Make sure the team agrees this is the shared version that works for most people most of the time.
  • You can always have your own version. A personal skill tailored to your preferences can coexist with a shared team skill. Your personal version takes priority in your conversations.
  • You're responsible for keeping it current. If a template, process, or standard changes, the shared skill needs to reflect that — otherwise teammates are working from outdated instructions.
