How to Use This Library

This library turns what you practiced in Business Requirements Management into prompts you can use on a real project, with Copilot.

It follows the same arc as the class: start with stakeholders, plan your approach, define success, build the foundation and frame, elicit, write and check requirements, facilitate the room, manage change, and prepare for testing. Use the menu on the left to jump to the step you need.

Every prompt is tagged one of two ways:

Prompt to run

The AI produces something for you: a list, a draft, an analysis. Paste it in, fill the bracketed slots, and go.

Guided conversation

The AI leads a working conversation, asking one question at a time. It should not jump to a finished answer. You think out loud; it helps.

Where to start

Run Build Your Project Brief first — it is the last item in this Start Here section. Most prompts ask for that brief, and everything gets easier once you have it. Save it where you can reach it, or keep it in a Copilot Notebook.

Then consider copy/pasting the Evaluate (and Fix) a Requirement prompt somewhere you can find it easily. It is the everyday workhorse: paste in any requirement and it scores that requirement against the five qualities from class, then suggests a cleaner version.

Keep the judgment

The AI drafts; you decide. Stakeholder lists, drivers, and requirements only count once real stakeholders have confirmed them. Treat everything these prompts produce as fodder for the conversation, not a substitute for it.

The most expensive project surprise is an overlooked or misunderstood stakeholder.

Tip: Keep Chats Short

The single easiest way to get better answers: keep each chat focused on one task.

Long chats make it harder for the AI to remember what is important, which increases the chance of hallucination or output that is not useful. To fix this, start a new chat whenever you are switching topics or using a new prompt.

Carrying your context across chats

Because you will be starting fresh often, you need a way to give the AI your project background without retyping it. Two options:

Option A · Copilot Notebook
  • Add your project brief and a few key project files once. Copilot stays grounded in them across every chat in that notebook, so you do not have to paste anything.
Option B · Paste the brief
  • If you are not using a notebook, keep your project brief handy and paste it wherever a prompt asks for it.
  • That is what the project brief line in these prompts is for.

Run Build Your Project Brief (the last item in Start Here) early. Everything else gets easier once you have that brief.

When a chat gets long, this writes a handoff summary you can paste as the first message in a fresh chat, so you pick up without re-explaining.

Prompt
You are helping me move from this chat to a fresh one without losing the thread.

Task: Write a compact handoff summary of this conversation that I can paste as the first message in a new chat.

Include:
- What I am working on and the goal of this thread.
- The key decisions or conclusions we reached.
- Any important details, numbers, or constraints that came up.

Guidelines:
- Keep it tight and skimmable. Bullets, not prose.
- Write it as a briefing to a fresh AI chat, so it has everything it needs to continue.

Build Your Project Brief

Guided conversation

Run this first. It interviews you about your project and writes a tight, reusable brief you can paste into the other prompts, or save in a Copilot Notebook.

Guided conversation

The AI will lead, asking one question at a time. Answer as you go. It should not jump to a finished answer.

Prompt
You are an experienced project consultant helping me capture the essentials of my project in a short, reusable brief.

I want you to interview me, then write a clean project brief I can reuse across other prompts and chats.

How to run this:
- Lead a focused conversation. Ask me one question at a time and wait for my answer before the next. Do not write the brief until you have what you need.
- Cover, in roughly this order: what the project is and the outcome it must deliver; the sponsor and key stakeholders and what each cares about; the timeline and any hard deadlines; the budget or resource picture; the current status and stage; the biggest risks or unknowns; and any constraints (tools, compliance, dependencies).
- Ask a follow-up only where my answer is vague or leaves an obvious gap. Keep it moving. This should take a few minutes, not an interrogation.

When you have enough, write the brief:
- Use clear headers and short bullets. Keep it to about one page.
- Write it so a colleague, or a fresh AI chat, could understand my project cold.
- End with a one-line summary I can use as a quick reference.

Guidelines:
- Do not invent details. If I do not know something, mark it as open.
- Plain language. No jargon I did not use myself.

Start by asking your first question.
Start with Stakeholders

Find the Missed Stakeholders

Prompt to run

Missed requirements come from missed stakeholders. This prompt helps surface the people you are most likely to overlook.

Prompt
You are a seasoned business analyst helping me build a thorough first-draft stakeholder list, including the people I am most likely to overlook.

MY PROJECT BRIEF:
[Paste your project brief here. If you saved it in a Copilot Notebook, tell me to use the brief in this notebook instead.]

The principle: missed requirements come from missed stakeholders.

How to run this:
1. First, ask me 2 to 3 questions to understand my project well enough to do this well — for example, what changes and for whom, what systems or data are involved, and who is downstream of the result. Wait for my answers.
2. Then produce an initial stakeholder list. For each stakeholder, tag which of these four tests they meet (one or more):
   - You need their cooperation.
   - Their requirements shape the solution.
   - Their opposition can impact project success.
   - Their work is impacted by what you build.

Make the list:
- Thorough. Include the obvious players and the easily forgotten ones: downstream report consumers, compliance and audit, people running workarounds or "secret spreadsheets" today, trainers and support staff, and anyone whose data feeds or is fed by the system.
- Specific. Name roles precisely — "data architect," not "technical team"; "regional compliance lead," not "compliance."

Guidelines:
- Mark every entry as a hypothesis for me to confirm, not a fact.
- End with the saturation technique I can use to validate and extend the list: ask each stakeholder, "Think forward to when we roll this out. Who would be upset if they had not been consulted?" Then ask each person they name the same question, and stop when the same names keep coming back.

Map Stakeholder Drivers

Prompt to run

Hypothesizes what each stakeholder is likely to care about based on their role, flags where drivers collide, and hands you a stakeholder register for your spreadsheet.

Prompt
You are a business analyst helping me think through what my stakeholders are likely to care about, based on their role.

MY PROJECT BRIEF:
[Paste your project brief here. If you saved it in a Copilot Notebook, tell me to use the brief in this notebook instead.]

MY STAKEHOLDER LIST:
[Paste your stakeholder list, with a few words on each person or group's role.]

Drivers are the specific things stakeholders care about, and they can shift during a project. Examples: minimizing change, protection from errors, finishing on time, gaining advanced capabilities, control, job security, trustworthy data.

Task:
1. For each stakeholder or group, hypothesize their two or three most likely drivers based on their role and what the project asks of them — not on guesses about their personality or background. Give a one-line reason tied to the role for each.
2. Flag where drivers are likely to conflict between stakeholders. These are competing drivers I will need to escalate and resolve, or manage as risks.
3. Output the result as a stakeholder register I can drop into a spreadsheet: one row per stakeholder, with columns for Stakeholder / Role, Likely Drivers, Why (tied to role), Potential Conflicts, and Questions to Validate. Format it as a table.

Guidelines:
- These are role-based hypotheses to validate in conversation, not conclusions about individuals. Say so at the top.
- For each stakeholder, give me one or two interview questions I could use to confirm their actual drivers.
Plan Your Approach

Draft Your Requirements Plan

Guided conversation

Walks you through the full requirements process — define, gather, prioritize, verify, validate, test — one decision at a time, then writes a one-page plan.

Guided conversation

The AI will lead, asking one question at a time. Answer as you go. It should not jump to a finished answer.

Prompt
You are an experienced business analyst helping me plan how I will gather and manage requirements on my project, end to end.

MY PROJECT BRIEF:
[Paste your project brief here. If you saved it in a Copilot Notebook, tell me to use the brief in this notebook instead.]

How to run this:
- Interview me one question at a time, walking through the six phases of a requirements process. Do not write the plan until we have covered them all.
- Define: How will I set high-level scope and out-of-scope items? How will I identify stakeholders, risks, and assumptions? What development approach and life cycle fits? What are the high-level business requirements and success factors?
- Gather: Will I map current processes? How will I capture scenarios and user stories? How will I elicit stakeholder, solution (functional and non-functional), and transition requirements? Where will requirements be documented and stored (spreadsheet, requirements tool, or other)?
- Prioritize: What method will I use, and who is in the room when priorities are set?
- Verify: How will I check that requirements meet quality criteria before they are baselined?
- Validate: How will I check that requirements meet the business goals and objectives?
- Test: How will I keep traceability between requirements, product features, and tests, and what is my role in supporting testing?

Keep it proportionate:
- A simple project does not need a heavyweight plan, and a complicated process may need more structure and rigor. Flex the depth of each phase to the nature of my project, and ask me about that as we go.

When we have covered the phases, write a one-page requirements management plan with clear headers, short bullets, and open items clearly marked. End with the three biggest risks to this plan and how I would spot them early.

Start by asking your first question.
Define Success

Draft an Outcome Statement

Guided conversation

Turns a fuzzy success definition like "a reliable and modern system" into an outcome statement that is simple, spare, and observable.

Guided conversation

The AI will lead, asking one question at a time. Answer as you go. It should not jump to a finished answer.

Prompt
You are helping me turn a fuzzy project goal into a clear outcome statement.

What an outcome statement is:
- It concisely summarizes the desired end state and the purpose behind it.
- It is written in the present tense, as if we are living in the end state right now: "Success looks like [desired end state]."
- It is simple, spare, and observable. An example of a good one: "Six months after go-live, supervisors can document safety incidents and share them with operations and compliance teams within one hour of occurrence, compared to the current average of 24 hours."

THE FUZZY SUCCESS DEFINITION I AM STARTING FROM:
[Paste what the sponsor or stakeholders have said success looks like, even if vague. For example, "a reliable and modern inventory system."]

How to run this:
- Interview me one question at a time. Push from adjectives to observable behavior. Cover: who can do what differently in the end state; what they can observe from their own seat; by when, and against what current baseline; what threshold or number would make it real; and what is deliberately NOT part of success this time.
- When an answer is an adjective like "reliable," "modern," or "efficient," ask what someone would see or measure that proves it.

When you have enough:
- Draft two or three candidate outcome statements, present tense, simple, spare, observable.
- Check each candidate against those three tests and say plainly where it falls short.
- If I have more than one desired outcome, remind me that each outcome has the potential to compromise the others without clear prioritization, and ask me to rank them.

End with the follow-up questions I should still take to my sponsor before treating this as agreed.

Pressure-Test Competing Drivers

Prompt to run

Takes your success definition and asks, for each stakeholder: what does this cost them, or fail to give them? Conflicts surface now, while you can still act.

Prompt
You are a candid advisor helping me pressure-test my project's definition of success before it hardens.

MY PROJECT BRIEF:
[Paste your project brief here. If you saved it in a Copilot Notebook, tell me to use the brief in this notebook instead.]

THE SUCCESS DEFINITION / OUTCOME STATEMENT:
[Paste it.]

THE STAKEHOLDERS TO TEST IT AGAINST:
[List the executives and stakeholder groups. For example: CFO, Compliance/Legal, Head of Field Operations, IT Security, a newly hired transformation executive.]

Task: For each stakeholder, ask the class question: what does this definition of success cost them, or fail to give them?

Produce a table with: stakeholder; what this definition costs them or fails to give them; how that is likely to show up (quiet resistance, escalation, competing requirements, scope pressure); and how serious it is.

Then split the conflicts into two lists:
1. Escalate and resolve now: conflicts that need a decision from the sponsor or between executives before requirements gathering goes further.
2. Manage as risks: conflicts that cannot be resolved yet. Write each as a one-line risk statement I can put on the risk register.

Guidelines:
- Do not soften. The point is to surface the competing drivers now, while I can still act.
- Where a conflict could be eased by rewording the outcome statement rather than changing the substance, suggest the rewording and say what it does and does not fix.
Foundation & Frame

Build a Context Diagram

Prompt to run

The foundation. Drafts your context diagram in text form — the system in the middle, every entity around it, and the labeled relationships between — so you can see every domain where requirements must be gathered.

Prompt
You are a business analyst helping me build a context diagram for my solution.

What a context diagram is: one system in the middle, the people and systems outside it that interact with it, and a labeled arrow for each relationship. It sets the boundary between what is inside the system and what is outside. An entity can be a person, system, department, or external organization — anything the solution interacts with that needs requirements attached to it. The arrows label relationships, not just process steps: a single arrow might represent a piece of data, an action, or a process. The diagram is detailed enough when it captures a complete list of domains where requirements will need to be gathered.

MY PROJECT BRIEF:
[Paste your project brief here. If you saved it in a Copilot Notebook, tell me to use the brief in this notebook instead.]

WHAT I KNOW SO FAR ABOUT THE SYSTEM AND WHO TOUCHES IT:
[Anything you have: the entities you have identified, current systems, departments involved. A partial list is fine — finding the gaps is the point.]

Task:
1. Name the system in the middle.
2. List the entities around it. Include the ones I gave you and add the ones I am likely missing. Check the commonly forgotten: compliance and audit, downstream reporting consumers, vendors and external organizations, adjacent systems that feed or consume data, support and help desk, and anyone running a workaround today.
3. For each entity, describe its relationship(s) to the system as labeled arrows in this form: Entity -> System: [label]. System -> Entity: [label]. The label can name data, an action, or a process — whatever that arrow represents.
4. Mark each entity I did not mention with [PROPOSED] so I can confirm or reject it.

Guidelines:
- The output should be clean enough that I can redraw it as a diagram on a whiteboard or slide in a few minutes.
- End with: (a) any entities you suspect exist but cannot confirm from what I gave you, phrased as questions to take to stakeholders, and (b) the reminder question: "Does this capture every domain where requirements need to be gathered?"

Flex the Plan to Problem Type

Prompt to run

Sorts the aspects of your project — often the relationships on your context diagram — into simple, complicated, and complex, then recommends how much requirements rigor each deserves.

Prompt
You are a business analysis advisor helping me right-size my requirements approach.

The depth and rigor of requirements gathering depends on the type of problem each part of the project is solving:
- Simple: the path is clear and repeatable. Stay light. Discovery and documentation can be lighter; use templates or repeatable requirements where you can.
- Complicated: expert-dependent, many moving parts, but figure-out-able. Increase rigor: SME interviews, current-state mapping, a fuller requirements set.
- Complex: the path is not knowable up front; you learn as you go. Iterate: prototypes, focus groups, smaller execution iterations.

MY PROJECT BRIEF:
[Paste your project brief here. If you saved it in a Copilot Notebook, tell me to use the brief in this notebook instead.]

MY CONTEXT DIAGRAM (if I have one):
[Paste your context diagram entities and relationships. The "aspects" below often line up with the relationships on it.]

By "aspect," I mean a distinct part of the work I would actually plan and manage — often one of the relationships or processes on the context diagram. For example, on an inventory project, "submit a work order" or "transfer spare parts between sites" are aspects. They are not all the same problem type: a documented, repeatable submission may be simple, while reconciling counts across sites whose numbers disagree may be complex.

Task:
1. Break my project into its main aspects, drawing on my context diagram where I gave you one.
2. Sort each aspect into Simple, Complicated, or Complex, with a one-line reason.
3. For each aspect, recommend the requirements approach that fits: how I should discover requirements there, how heavy the documentation should be, and what elicitation techniques fit.

Guidelines:
- If an aspect is a mix, say so and split it.
- Watch for the traps: oversimplifying or under-specifying complicated problems has consequences; overplanning complex work creates false confidence and low awareness when requirements have changed. Flag any traps you see in my project.
- Ask me up to two clarifying questions first only if you genuinely cannot sort the work without them. Otherwise, proceed.

Draft Scenarios

Prompt to run

The frame. Drafts plain-language, real-life scenarios for one domain of your context diagram — graded against what makes a good scenario before they reach you, and weighted toward the exception paths that expose hidden requirements.

Prompt
You are a business analyst helping me draft scenarios for requirements discovery.

What a scenario is: a real-life, operational situation described in plain language. A good one names the role, the place, and the real conditions, plus the other specifics that drive requirements. For example: "Marcus, a field technician, is assigned a quarterly preventive maintenance task on a compressor unit at a station two hours out, where there is no cell or wifi coverage. He works through the checklist, records readings, notes the filters he replaced from truck stock, and leaves the site before he is back in coverage."

MY PROJECT BRIEF:
[Paste your project brief here. If you saved it in a Copilot Notebook, tell me to use the brief in this notebook instead.]

THE DOMAIN I AM WORKING ON:
[Name one entity or domain from your context diagram. For example, "Field Technician" or "Procurement."]

Task: Draft 6 to 8 scenarios for this domain.
- One or two should be the happy path.
- The rest should be exceptions and non-happy paths: the part is not available, the approver is out, the connection drops, the data arrives wrong, the timing collides with something else. Exceptions are where the requirements hide.
- Each scenario: a short title, then 3 to 6 sentences in plain language with a named role, a specific place or condition, and what happens. No requirements language yet — scenarios are a discovery tool.

Before you show me a scenario, grade it against these criteria, and only present scenarios that pass (revise or drop the rest):
- Specific: it names the role, the place, and the real conditions, not a generic situation.
- Plain language: it reads as a story, not as a list of requirements or system behaviors.
- Useful: it would plausibly surface a requirement — especially an exception a happy-path-only view would miss.
- Grounded: it fits my project's reality. If you had to guess at an operational detail, mark it with [?] so I can correct it.

After the scenarios:
- For each, list what it would force a solution to handle, as a teaser for the requirements to come.
- Remind me: enough scenarios is when new scenarios stop surfacing new requirements. And keep them — they pay off twice, including as vendor demo scripts where you ask how the tool handles each one out of the box, with configuration, or only with customization.
- Ask which scenarios ring true, which are off, and offer to draft more for the gaps I name.

Write User Stories

Prompt to run

A lighter alternative to scenarios. Drafts user stories in the classic form — as a [role], I want [capability], so that [benefit] — to capture needs quickly from each user's point of view.

Prompt
You are a business analyst helping me write user stories.

What a user story is: a need stated from a particular user's point of view, in the form "As a [role], I want [capability], so that [benefit]." For example: "As a compliance specialist, I want to see which assets are at risk of exceeding acceptable late-maintenance thresholds so that I can escalate this to site supervisors." A user story is a lighter alternative to a scenario — use it when you want to capture needs quickly from each user's perspective rather than walking through full situations.

MY PROJECT BRIEF:
[Paste your project brief here. If you saved it in a Copilot Notebook, tell me to use the brief in this notebook instead.]

THE DOMAIN I AM WORKING ON:
[Name the domain or area from your context diagram, and the roles who interact with it.]

Task: Draft 6 to 10 user stories for this domain.

Guidelines:
- Cover more than one role. If every story is from the same seat, say so and suggest whose perspective is missing.
- The "so that" must carry real benefit. Reject circular benefits that just restate the want ("I want to export data so that I can export data"). Every benefit should answer: what does this let the person do, avoid, or decide?
- Flag any story that is actually a business rule (a policy the solution must enforce) in disguise, and restate it as what it really is.
- Mark anything you inferred rather than took from my materials with [PROPOSED].
- End by asking which roles or situations I think are still uncovered, and offer to draft stories for them.
Requirements Elicitation

Build an Interview Guide

Prompt to run

Builds a question guide for a stakeholder interview or focus group — shaped to your purpose, scaled to your time, mixing fact-finding and deeper, probing questions.

Prompt
You are an experienced business analyst helping me build a question guide for a requirements interview.

WHAT I AM TRYING TO ACCOMPLISH (my purpose):
[Describe what this session is for — for example, "walk through the work-order approval process end to end" or "understand the pain points of the field technician group."]

WHO WILL BE IN THE ROOM:
[The role(s). It may be one person, or a group — a panel interview or a focus group. Note which.]

MY PROJECT BRIEF (optional):
[Paste it, or tell me to use the brief in my Copilot Notebook.]

How to run this:
1. First, ask me two things and wait for my answers: what outcome I want to walk away from this session with, and how long the session is.
2. Then build the question guide.

Build the guide to fit the purpose and the time:
- Follow a logical flow. A session to walk through a process end to end needs a different question set than one to surface a user group's pain points. Shape the flow to the purpose I gave you.
- Mix the question types. Not every question should be a deep, probing one. Open with fact-finding and level-setting questions to establish shared understanding, then move into the deeper questions that dig into drivers, frictions, and assumptions.
- Scale the number of questions to the time I have, accounting for how much discussion each question is likely to generate. A 30-minute interview and a 90-minute workshop should not have the same number of questions.

For the deeper questions, lean on what makes a good question: it invites engagement, even disagreement; it digs past the first answer (the five whys is one way); and it surfaces the buried assumptions that sink projects. Include at least one question that surfaces workarounds, for example: "When the current system can't give you what you need, walk me through what you actually do."

Close the guide with the saturation question: "Think forward to rollout. Who would be upset if they had not been consulted?"

Also give me: a one-line statement of the session's purpose and desired outcome I can send with the invite, and one polite redirect line for when the conversation drifts into a gripe session.

Practice the Interview

Guided conversation

The AI plays your stakeholder — vague first answers, a workaround they don't volunteer, a driver they don't state — and you practice digging. Then it debriefs you.

Guided conversation

This one is a role-play. The AI stays in character as your stakeholder until you say "debrief." Treat it like the real interview: dig past the first answer.

Prompt
You are going to play a stakeholder so I can practice a requirements interview. I am the interviewer.

MY PROJECT BRIEF:
[Paste your project brief here. If you saved it in a Copilot Notebook, tell me to use the brief in this notebook instead.]

Setup:
- First, ask me two things: who you should play (role, and a temperament: cooperative, rushed, reserved, skeptical, or know-it-all — or tell you to pick), and what I want to get out of the interview. Then begin.

How to play it:
- Stay in character. Answer like a real, busy person: first answers are short and surface-level, you use your own shorthand, and you do not organize your thoughts for me.
- Build in, without announcing them: one workaround you use today (a side spreadsheet, an off-system phone call, a manual fix) that you only reveal if I dig into how the work actually happens; one driver you care about (protection from errors, minimizing change, control, finishing on time) that you never state directly but that colors your answers; and one assumption you hold about the new solution that is plausibly wrong.
- Do not make it easy, and do not be a cartoon. If I ask a good open question, reward it with real material. If I ask a leading or closed question, give me the thin answer it deserves.

When I say "debrief" (or after about 12 exchanges, offer it):
- Step out of character. Tell me: whether I dug past first answers or accepted them; whether I found your hidden workaround, your unstated driver, and your wrong assumption; which of my questions invited engagement and which put you on the defensive; and the single requirement I would most likely have missed based on how the interview went.
- Show me two of my questions rewritten the way a skilled interviewer would have asked them.
- Offer to run it again with a different temperament.
Write & Check Requirements

Evaluate (and Fix) a Requirement

Prompt to run

The everyday workhorse. Paste any requirement and it gets classified, scored against the five qualities from class, rewritten to pass, and checked for the business rules hiding underneath.

The five qualities

Unambiguous · Testable · Independent · Atomic · Implementation-free. A requirement that "mostly works" fails.

Prompt
You are a tough, constructive requirements quality reviewer. Evaluate the requirement(s) below against the criteria from my training, then suggest a revised version of each.

THE REQUIREMENT(S):
[Paste one requirement, or several. Numbered is easiest.]

CONTEXT (optional but helps):
[A line or two on the project or system, or paste your project brief. If you saved it in a Copilot Notebook, tell me to use the brief in this notebook instead.]

For each requirement, do four things:

1. CLASSIFY IT. Which is it, and is it written in the right form for its type?
- Business requirement: the why. Written as a "To..." statement. ("To reduce equipment downtime, the maintenance team needs field work completed and recorded reliably, even with no connectivity.")
- Functional requirement: an action, process, or interaction. Written as a "shall" statement. ("The system shall not allow creation of a part transfer request if an associated work order is not in the system with a status of 'approved.'")
- Non-functional requirement: a quality or environmental condition. Written as a constraint with a measurable threshold. ("On reconnect, the system shall sync a completed work order within 30 seconds on a standard field connection.")
- Transition requirement: a temporary capability needed to get from current to future state. A plain sentence. ("Field technicians shall complete a two-hour training on the new work order app before go-live.")
- Or actually a business rule (a policy, limit, or approval the organization enforces) wearing a requirement costume. If so, say so.

2. SCORE IT against the five qualities. For each: pass or fail, with one line of evidence.
- Unambiguous: one meaning, not two. Could three builders build three different things? Does it say exactly what happens in every case (reject vs. truncate vs. warn)?
- Testable: you can check whether it was met. "Etc.," "quickly," "user-friendly," "robust," and "as appropriate" all fail.
- Independent: it stands on its own without depending on a neighboring requirement to make sense.
- Atomic: one requirement, not several bundled into one sentence. Bundles are harder to test.
- Implementation-free: it states the capability or need, not the technology or solution. "Stored in a text file" locks the how.

3. REWRITE IT. Give a revised version that passes all five qualities, in the correct form for its type.
- If it fails Atomic, split it into separately numbered requirements.
- Do not invent specifics I never gave you. Where a threshold, role, or behavior is missing, put a [bracketed placeholder] in the rewrite and list the exact questions I need to answer to fill it.

4. FLAG THE BUSINESS RULES. Note any business rule (a policy, limit, approval, or calculation the solution must enforce) that the requirement implies but does not state explicitly — these deserve their own callout so they are captured, not assumed. Also note any assumption a stakeholder would need to confirm. (Data the requirement depends on can live inside the functional requirement; just make sure it is explicit rather than implied.)

Guidelines:
- Be a tough grader. The fix for ambiguity is to say exactly what happens and name every case.
- If I pasted several requirements, evaluate each one, then end with any inconsistencies or overlaps between them.

Turn a Scenario into Requirements

Prompt to run

Prepare for Testing

Turn Scenarios into Use Cases

Prompt to run

Groups your related scenarios into use cases — the straightforward path as the main flow, the variations and exceptions as alternate flows — the structured backbone builders and testers work from.

Prompt
You are a business analyst helping me turn my scenarios into use cases.

What a use case is: a structured, step-by-step description of how a goal gets accomplished. Related scenarios belong together in one use case — the straightforward path is the main flow, and the variations and exceptions become alternate flows. A use case has this shape:
- Name / Goal: what is being accomplished, in plain terms.
- Actor: who performs it.
- Preconditions: what must be true before it starts.
- Main flow: the step-by-step happy path (Actor does X -> system does Y -> ...).
- Alternate flows: the variations and exceptions, each tracing back to a scenario (for example: if stock is below the requested quantity, the system blocks the transfer and alerts the operator).
- Postconditions: what is true once it is done.

MY SCENARIOS:
[Paste the related scenarios you want turned into use cases. If they are saved in a Copilot Notebook, tell me to use the files in this notebook instead.]

Task:
1. Group my scenarios into use cases. Scenarios that share a goal belong in one use case — the main path as the main flow, the rest as alternate flows. Tell me which scenarios you grouped together and why.
2. Write each use case in the structure above.
3. Where a scenario implies a step or condition that is missing, mark it with [?] rather than inventing it, and list what I need to confirm.

Guidelines:
- Keep the main flow to the clean, expected path. Push variations and exceptions into alternate flows so the use case stays readable.
- If a set of scenarios does not actually share a goal, say so and keep them as separate use cases rather than forcing them together.
- End by noting any goal that my scenarios only partly cover, so I can see where a scenario is still missing.
